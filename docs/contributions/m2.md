## Business rule I own
**Condition 2: a venue is never committed to overlapping active bookings.** Two bookings overlap when `new.start < old.end AND old.start < new.end`. Only PENDING and CONFIRMED events count, so rejecting or cancelling releases the slot without any extra code.

## Assumption / trade-off
- **Back-to-back bookings are allowed** (half-open intervals, A1). One event can end at 12:00 and the next start at 12:00.
- **All problems are reported together**, but follow-on checks are skipped. For example, availability isn't checked when end is before start, because those messages would be misleading. The trade-off is slightly more branching in `validate_request` in exchange for clearer messages.
- **`exclude_event_id` exists** because the Step 3 approval re-check would otherwise find the pending request in conflict with itself.

## How I validated it
- **Validated the previous step:** pulled Step 1, ran `pytest -q` (34 passed) and `python -m cems.seed`.
- **Boundary tests:** the seeded Seminar Hall A booking (10:00–12:00) is checked against 8 cases (overlapping the start, the end, inside, enclosing, identical, ending at 10:00, starting at 12:00, a different day). There are similar tests for the renovation block, and one test per status showing that only PENDING and CONFIRMED hold the venue.
- **Mutation check:** I changed `<` to `<=` in the overlap SQL. 3 tests failed, which proves the boundary tests catch that bug. Then I reverted the change.
- **Result:** `pytest -q` → 90 passed.

## AI suggestion I corrected
The AI-suggested overlap check used `start_at <= ? AND ? <= end_at`. That treats back-to-back bookings (12:00 end, 12:00 start) as conflicts, which contradicts assumption A1. I changed it to strict `<` and added tests for both edges.
