# M4: Step 4, Streamlit App and Requester Experience

## What I built
- **`app.py`**: the Streamlit entry point.
  - One cached SQLite connection, created and seeded on first run.
  - `CEMS_DB_PATH` overrides the database file.
  - Sidebar role selector (Requester / Reviewer / Facilities Manager) and a name field.
  - Routes to each role's page. Reviewer and Facilities show a placeholder until Step 5.
- **`ui/requester.py`**:
  - **New request** form with a **live pre-check**. Every change re-runs `rules.validate_request`, problems are listed in red, and Submit is disabled until there are none. A panel shows what already occupies the chosen venue that day.
  - **My requests**: counts by status, a status badge per request, the rejection reason, and a **Cancel event** button for confirmed events.
- **`ui/common.py`**: status badges, venue labels, and flash messages for callbacks. Reused by the Step 5–7 pages.
- **`tests/test_app_requester.py`**: 12 headless UI tests using Streamlit's `AppTest`.
- README "Using the app" section with demo scenarios; assumptions A15–A17; UI conventions in CLAUDE.md.

## Business rule I own
**Condition 3: a conflicting request must be prevented before it is submitted.** The form uses plain widgets instead of `st.form`. `st.form` would only validate after Submit is pressed; plain widgets re-run the check on every change, so a conflicting request can never be sent. `services.submit_request` still re-validates inside its transaction, in case the slot is taken between the page loading and the click.

## Assumption / trade-off
- **A16, no login:** the organiser is whoever is named in the sidebar. This is simple to demo, but anyone can act as any club. It's documented as a limitation; SSO is a next step.
- **A15, one date per event:** the form has one date and two times. That fits the 12-hour maximum and keeps the form short.
- **Writes happen in `on_click` callbacks** with flash messages. Callbacks run before the page re-runs, so the title field can be cleared after a submit and the message appears exactly once.

## AI suggestion I corrected
The AI first generated the request form inside `st.form`. That meant conflicts only appeared after pressing Submit, which breaks condition 3 ("prevented *before* it is submitted"). I rebuilt it with plain widgets, a live check and a disabled Submit button.
