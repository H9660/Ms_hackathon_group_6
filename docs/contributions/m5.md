# M5: Step 5, Reviewer and Facilities Manager

## What I built
- **`cems/venue_service.py`**:
  - `add_block`: requires a reason and a valid window. It is refused over any PENDING or CONFIRMED booking, and the error lists those bookings. Blocks may span several days.
  - `remove_block`: lifts a block; supported by `repository.delete_block`.
- **`ui/reviewer.py`**: three tabs.
  - **Pending review**: approve, or reject with a required reason, plus each request's history. Approve is disabled, with an explanation, if the slot is no longer available.
  - **Confirmed**: the Events Office can cancel any event.
  - **All requests**: a table of every request.
- **`ui/facilities.py`**:
  - venue table and current blocks, each with a **Remove block** button;
  - **Block a venue** form (maintenance / renovation / other, plus details), with a live warning that lists any bookings in the way.
- **`app.py`**: routes all three roles, and adds a sidebar **Reset demo data** button.
- **Tests:** `tests/test_blocks.py` (14 tests) and `tests/test_app_reviewer_facilities.py` (10 UI tests). The suite now has 151 tests.
- **Docs:** README usage steps 4–6 with an end-to-end demo script; assumptions A18–A20.

## Business rule I own
**Condition 4, together with assumption A5: a venue can be blocked, but never over an active booking.** If a block could overlap a confirmed event, the venue would be both committed and unavailable, which breaks condition 2. So `add_block` lists the bookings in the way, and Facilities must have them cancelled or rejected first.

## Assumption / trade-off
- **A18:** blocks have no 12-hour limit, because renovations take days. Events keep the limit.
- **A19:** blocks can be removed. Without this, a venue would stay unavailable after work finished early, which the brief lists as a pain point.
- **Trade-off:** blocks are not written to the audit log, which only tracks events. That kept the schema unchanged, at the cost of no history for who blocked a venue. Listed as a next step.

  1. Requester submits.
  2. Reviewer approves.
  3. Facilities' block is refused.
  4. Requester cancels.
  5. Facilities' block is now accepted.

  The event's history read SUBMITTED → APPROVED → CANCELLED, with no exceptions.
