# M3: Step 3, Workflow State Machine

## What I built
- `cems/services.py`: the only module that changes an event's status.
  - `submit_request`: validate, then store as PENDING and write to the audit log.
  - `approve_request`: PENDING → CONFIRMED, re-checking availability while excluding the request itself.
  - `reject_request`: PENDING → REJECTED, with a required reason.
  - `cancel_event`: CONFIRMED → CANCELLED, allowed for the organiser or a Reviewer.
  - `BookingError`: a single error type whose `reasons` list is ready to show in the UI.
- `tests/test_lifecycle.py`: 25 tests covering the end-to-end flows, every invalid transition, required inputs and rollback.
- README "Event lifecycle" section with a Mermaid state diagram and workflow table; assumptions A12–A14.

## Business rule I own
**Condition 5: a request must be reviewed before it becomes a confirmed event.** The only path to CONFIRMED is `approve_request`, and only from PENDING. Rejected, cancelled and confirmed requests cannot be reviewed again, so the state machine has no hidden shortcuts.

## Assumption / trade-off
- **Each operation is one `BEGIN IMMEDIATE` transaction.** The write lock is taken before the checks run, so two people cannot both pass the conflict check for the same slot. The trade-off is that writers are serialised and a second writer waits up to 5 s. That's fine for a campus booking tool, and it guarantees condition 2.
- **Approval re-checks availability.** This is defence in depth: submit already prevents conflicts, but approval is the moment a booking becomes binding.

## How I validated it
- **Validated the previous step:** pulled Step 2 and ran `pytest -q` (90 passed). I also confirmed that `check_availability(..., exclude_event_id=...)` covers what approval needs.
- **End-to-end tests:**
  - submit → approve → cancel → the same slot can be booked again;
  - submit → reject → another organiser books the slot;
  - cancelling the seeded Seminar Hall A event frees its slot.
- **Invalid transitions:** approve or reject after either decision, cancel while pending, cancel twice, cancel by the wrong requester. In each case the status is unchanged afterwards.
- **Atomicity:**
  - a test makes the audit log fail after the insert and checks that no event row remains;
  - a manual two-connection check: while another connection held the write lock, `submit_request` waited and then failed with `database is locked`, leaving nothing behind;
  - once the lock was released, the submit succeeded.
- **Result:** `pytest -q` → 115 passed.
