How we worked

We split the work into 7 incremental steps, one member per step and one commit per step. Each member:

  1. pulled the previous step;
  2. validated it (ran pytest -q and the app);
  3. built their step on top;
  4. tested;
  5. committed and pushed.

Every commit leaves the project working and green. That is why the git history reads as a clean build-up: data → rules → workflow → first UI → full lifecycle UI → bonus → visibility and deliverables.

Why this split works

  • Each step owns its own files, so work never collided.
  • The interface was agreed up front (PLAN.md §3), so everyone could draft against it early.
  • Each step adds one layer of value you can demo: tests at Steps 1–3, browser UI from Step 4.
  • The next member validates the previous step, so every handover was reviewed.

Shared conventions (CLAUDE.md)

  • Strict layering: ui → services → rules → repository → db → models.
  • Repositories never commit. Services own transactions.
  • Rules only read and return readable reasons.
  • Overlap is half-open (<, never <=).
  • SQL is always parameterised, and every widget has a stable key for tests.

Event lifecycle

new request— submit (all checks pass) → PENDING— approve → CONFIRMED— cancel → CANCELLED
PENDING— reject (reason required) → REJECTEDclosed. A revision is a new request.

The one idea to remember: only ACTIVE_STATUSES = (PENDING, CONFIRMED) hold a venue. The overlap query only counts those. So rejecting or cancelling releases the venue just by changing the status: no rows are deleted and no extra code is needed. Conditions 6 and 8 fall out of this one design choice.

Questions anyone may get

What happens if two people request the same slot at the same moment?

Both see the slot as free on screen, but each submit_request runs inside BEGIN IMMEDIATE, which takes SQLite's write lock before checking. The second submit waits for the first to commit, then re-runs the check, sees the first request as PENDING, and fails with "already booked … (PENDING)". A pending request already holds the slot, so the second person is told immediately.

How does rejecting or cancelling "release" the venue?

The overlap query only counts PENDING and CONFIRMED events. Changing the status to REJECTED or CANCELLED means the next conflict check simply no longer sees that event. Nothing is deleted, so the history is kept.

Why can't a requester edit a rejected request?

Condition 6 says a rejected request is closed and revisions need a new request. We have no edit function at any layer, so this can't be bypassed.

Why no authentication?

The brief marks it optional. With 90 minutes, we put the time into the complete lifecycle, the validations and the tests. A sidebar role selector stands in for login (A6). It's listed as the first next step (SSO).

Why SQLite and not JSON or in-memory storage?

It comes with Python and needs no setup. More importantly, it gives us transactions (check and write together), constraints (status values, end > start, capacity > 0) and foreign keys, all of which JSON files can't enforce.

Is 12:00–14:00 after a 10:00–12:00 booking a conflict?

No. We use half-open intervals (A1): overlap means new.start < old.end AND old.start < new.end, and 12:00 < 12:00 is false. Tests cover both edges, and a mutation check proves the tests would catch <=.

Why do past dates work?

The brief's data is in August 2026. Rejecting past dates would make its own scenarios impossible to demo, so we documented A4 and applied it consistently. In production this would be a one-line rule.

How did you use AI, and how did you keep control of it?

We wrote the interface contract and rules first, then gave them to the AI. Every member reviewed and ran the output and corrected at least one AI mistake, each recorded in docs/contributions/mN.md (see How we used AI). Tests, including mutation and rollback tests, were our main way of checking AI output.

How it works: what you must be able to explain

1. Times are stored as sortable text

Datetimes are stored as "2026-08-04T10:00". This format sorts in time order as plain text, so SQL comparisons like start_at < ? work directly on the stored values. Columns are called start_at / end_at because END is an SQL keyword.

2. The database also enforces the basics

status  TEXT NOT NULL CHECK (status IN ('PENDING','CONFIRMED','REJECTED','CANCELLED')),
attendees INTEGER NOT NULL CHECK (attendees > 0),
CHECK (end_at > start_at)
venue_id INTEGER NOT NULL REFERENCES venues(id)     -- with PRAGMA foreign_keys = ON

User-friendly messages come from rules.py. These constraints are the last line of defence if any code path skips the rules.

3. The transaction policy

conn = sqlite3.connect(path, isolation_level=None, check_same_thread=False)  # autocommit mode

@contextmanager
def transaction(conn, immediate=False):
    if conn.in_transaction:      # nested: join the outer transaction
        yield conn; return
    conn.execute("BEGIN IMMEDIATE" if immediate else "BEGIN")
    try:    yield conn
    except BaseException:
        conn.rollback(); raise
    conn.commit()
  • Autocommit mode (isolation_level=None) means we control exactly where transactions start.
  • immediate=True takes the write lock up front, which M3 uses to keep the check and the write together.
  • Nested calls join the outer transaction, so reset_db = clear_all + seed is atomic.
  • Repositories never commit; the caller does.
  • check_same_thread=False because Streamlit shares one cached connection across reruns.

4. Seeding is idempotent, and reset is safe

seed() does nothing if any venue exists. reset_db() deletes all rows in TABLES_CHILD_FIRST order (children before parents, so foreign keys hold), then seeds, in one transaction. Seeded events get a SEEDED audit entry by actor system.

Likely questions

Why is end not a column name?

END is an SQL keyword (CASE … END). start_at / end_at avoid quoting bugs.

What does transaction() do if called inside another transaction?

It joins the outer one: it doesn't begin or commit. If anything fails, the outer transaction rolls everything back together (tested in test_nested_transaction_joins_outer_and_rolls_back_together).

What if someone inserts an event with status "APPROVED"?

The database refuses it with an IntegrityError from the CHECK constraint (test_unknown_status_is_rejected). Our status is CONFIRMED, not APPROVED.

How do you know the seed data matches the brief?

test_seed.py asserts each venue's name, type and capacity, both confirmed events' exact times, the renovation block, and that the two "Available" venues have no bookings or blocks.

How it works

1. The overlap query (half-open intervals)

SELECT * FROM events
WHERE venue_id = ? AND status IN ('PENDING','CONFIRMED')
  AND start_at < :new_end AND :new_start < end_at
  [AND id != :exclude_event_id]

Two intervals overlap exactly when each starts before the other ends. That one condition covers every case: partly before, partly after, inside, enclosing and identical. With strict <, an event ending at 12:00 and one starting at 12:00 do not overlap.

Against Seminar Hall A 10:00–12:00Overlaps?
09:00–11:00 · 11:00–13:00 · 10:30–11:30 · 09:00–13:00 · 10:00–12:00Yes (all five)
08:00–10:00 · 12:00–14:00 · 10:00–12:00 on another dayNo

2. validate_request: every problem, in a sensible order

  1. Title required; organiser required; event type must be in EVENT_TYPES
  2. Time window: both times given, end > start, at most 12 h
  3. The venue exists. If not, stop here: capacity and availability need a venue
  4. Capacity: 1 ≤ attendees ≤ capacity
  5. Availability (overlaps + blocks). Only if the window is valid, otherwise the messages would be misleading

It returns list[str]; an empty list means valid. Because rules only read, the UI can call it on every keystroke (M4), the service re-runs it in the transaction (M3), and the reviewer page shows check_availability before Approve (M5).

3. Message quality (condition 10)

Seminar Hall A is already booked 04 Aug 2026 10:00–12:00 for 'Intro to Machine Learning Workshop' (CONFIRMED).
Conference Room C is unavailable 04 Aug 2026 09:00–18:00 (Renovation).
Innovation Lab holds 60 people; 80 expected attendees exceed its capacity.
Only the organiser (AI Club) or a Reviewer can cancel this event.

4. exclude_event_id

When M3 re-checks a pending request during approval, the request would find itself as a conflict. exclude_event_id skips it. You designed this in Step 2, ahead of when it was needed.

5. can_cancel

Only CONFIRMED events can be cancelled. A Reviewer can always cancel; a Requester only if name.strip().casefold() == organiser.strip().casefold() (A9). Facilities can't cancel.

Likely questions

Why does one condition cover all overlap cases?

Two intervals don't overlap only if one ends before the other starts: new.end ≤ old.start or old.end ≤ new.start. Negating that gives new.start < old.end AND old.start < new.end.

Does a rejected request still block the slot?

No. Only PENDING and CONFIRMED are in the query (test_rejected_or_cancelled_release_the_slot).

What if attendees equal capacity exactly?

Allowed: 500 people in the 500-seat auditorium passes (test_attendees_equal_to_capacity_is_allowed).

Why can't rules write anything?

So they're safe to call anywhere, any number of times, including on every UI rerun. Writes and transactions belong to services.

How it works

1. Every operation has the same shape

def approve_request(conn, event_id, actor):
    actor = _require_actor(actor)                       # name needed for the audit log
    with transaction(conn, immediate=True):             # take the write lock FIRST
        event = _load_event(conn, event_id)             # BookingError if missing
        _require_pending(event, "approved")             # state guard
        conflicts = rules.check_availability(conn, venue, event.start, event.end,
                                             exclude_event_id=event.id)
        if conflicts: raise BookingError([f"Cannot approve request #{event.id}:", *conflicts])
        repo.update_status(conn, event.id, Status.CONFIRMED)
        repo.log_action(conn, event.id, "APPROVED", actor)
        notify.notify(conn, event.organiser, "...approved...")   # added by M6

Validate inputs → lock → load → guard state → check rules → write → audit (→ notify). Any exception rolls back the whole block.

2. Why BEGIN IMMEDIATE

A normal BEGIN only takes the write lock at the first write. Two submits could both read "slot free" and then both insert. BEGIN IMMEDIATE takes the lock before the check, so writers run one after another: the second waits, then sees the first request as PENDING and is refused.

3. The guards

  • Approve and reject: only from PENDING. The message is "Only PENDING requests can be approved (request #3 is REJECTED)."
  • Cancel: rules.can_cancel, which allows CONFIRMED only, by the organiser or the Reviewer.
  • Reject: the reason is required and stripped. Every action: the actor name is required.

4. BookingError

One error type for every refusal. .reasons is a list[str] that the UI shows directly. It also accepts a single string.

One module owns all status changesNo hidden shortcuts to CONFIRMED; easy to audit and explain

Business rule you own

Condition 5: review is required before confirmation. The only path to CONFIRMED is approve_request, from PENDING. No other function sets CONFIRMED.

Assumption / trade-off

Writers run one at a time: a second writer waits up to 5 s (SQLite's default timeout), which is fine for a campus and guarantees no double booking. A7: a pending request cannot be withdrawn, which keeps the state machine small.
