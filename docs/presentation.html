Problem understanding

Key assumptions and the scope we chose for 90 minutes

Key assumptions (24 documented)

  • Half-open intervals: a booking ending at 12:00 and one starting at 12:00 don't clash
  • Attendees must fit: 1 ≤ attendees ≤ capacity; at most 12 h per event
  • Past dates are allowed: the brief's data is in Aug 2026
  • A block can't cover an active booking: cancel first
  • No login: a role selector stands in for authentication
  • Strict transitions: only PENDING can be reviewed; only CONFIRMED can be cancelled

In scope

  • Full request → review → cancel lifecycle
  • Conflict, block, capacity and time validation
  • Three role views + a public schedule
  • Bonus: in-app notifications

Out of scope

  • Partial or split bookings and suggestions (brief)
  • Editing requests (by design: condition 6)
  • SSO, recurring events, email or calendar

Solution

A layered architecture, so every part can be tested and explained

ui/ + app.pyStreamlit pages per role; writes only through services
▼
servicesState machine: the only place status changes
▼
rulesValidation: read-only, returns readable reasons
▼
repositorySQL ↔ dataclasses; no business rules, never commits
▼
db + modelsSQLite schema with constraints; enums and dataclasses

Why these choices

  • Python + Streamlit: a real UI in minutes; runs locally
  • SQLite: comes with Python; gives transactions, constraints and foreign keys, which JSON can't
  • Rules return reasons: the same checks power the live form, the save and the reviewer warning
  • No external services, as the brief requires
Each layer imports only from the layers below it6
Solution

Engineering decisions and trade-offs

1
All-or-nothing operations. Each change locks the database for writing (BEGIN IMMEDIATE) before its checks run, so two people can't book the same slot at once. The check, the write, the history entry and the notification succeed or fail together.
2
Releasing is a status change. The overlap query counts only PENDING and CONFIRMED, so nothing is deleted and the full history is kept.
3
Defence in depth. Live UI check → the service re-checks inside the lock → database constraints.
4
Re-check on approval, so a booking is valid at the moment it becomes binding.

Trade-offs we accepted

ChoiceCost
No loginAnyone can act as anyone
One writer at a timeOthers wait up to 5 s

Mutation check

We changed the overlap query's < to <= on purpose: 3 tests failed. The tests catch the classic back-to-back bug.

Concurrency check

While a second connection held the write lock, a submit waited, then failed cleanly with nothing written.

Rollback tests

Failures injected mid-operation (history log, notification store) undo the whole transition.
