Slide 1 · Problem Understanding

Campus events need one reliable path from request to decision

Campus Event Management System
Group 6 · IIIT Hackathon

1The problem & stakeholders

Events are coordinated through messages and spreadsheets. That causes conflicting venue requests, venues chosen without checking capacity, no visibility of request status, slow reviews, venues stuck after cancellations, and maintenance downtime nobody can see.

RequesterClub, faculty, placement cell. Requests a venue, tracks the outcome, cancels their own event
Event ReviewerEvents Office. Approves, or rejects with a reason; can cancel any confirmed event
Facilities ManagerBlocks venues for maintenance or renovation; lifts blocks
Campus communitySees each venue's schedule and which venues are free

2Workflows prioritised

Requestchecks pass →PENDINGapprove →CONFIRMEDcancel →CANCELLED
PENDINGreject + reason →REJECTEDclosed
  • The full lifecycle: submit → review → confirm or reject → cancel
  • Venue blocking for maintenance and renovation
  • A campus-wide schedule so everyone can see availability

3Business rules discovered

  • Only PENDING and CONFIRMED hold a venue; rejecting or cancelling releases it
  • Two bookings clash when each starts before the other ends (new.start < old.end ∧ old.start < new.end)
  • Conflicts, blocks, capacity and bad times are stopped before submit, each with a clear reason
  • Review is mandatory; a rejected request is closed, and a revision means a new request
  • Only the organiser or the Events Office can cancel; a block can't cover an active booking

4Key assumptions (24 documented)

  • Back-to-back bookings (12:00 end, 12:00 start) are allowed
  • 1 ≤ attendees ≤ capacity; at most 12 h per event, on one day
  • Past dates are allowed, because the brief's data is in Aug 2026
  • No login: a role selector stands in for it (auth is optional)

5Scope for 90 minutes

In: the full lifecycle, all conflict and failure handling, 3 role views + a public schedule, and a bonus (notifications).

Out: partial or split bookings and suggestions (brief), editing requests (condition 6), SSO, recurring events, email.

Initial data: 5 venues · Seminar Hall A booked 4 Aug 10–12 · Conference Room C renovation 4 Aug 09–18 · Innovation Lab booked 6 Aug 14–171 / 2
Slide 2 · Solution & Engineering Decisions

A layered Python app where every rule is enforced and tested

Python · Streamlit · SQLite
Runs locally · no external services

1High-level approach

ui/Streamlit page per role; live validation as you type
servicesState machine: the only place status changes
rulesRead-only checks that return readable reasons
repositorySQL ↔ data classes; never commits
SQLiteSchema with CHECK and foreign-key constraints

Bonus: in-app notifications. Reviewers learn about new requests; organisers learn the outcome, including the rejection reason.

2Key design decisions

  • All-or-nothing operations. Each change locks the database for writing (BEGIN IMMEDIATE) before its checks run, so two people can't book the same slot. The check, the write, the history entry and the notification succeed or fail together
  • Releasing is a status change. Nothing is deleted, so the full history is kept
  • Checked three times: live in the form, again by the service when saving, then by database constraints
  • Approval re-checks availability at the moment the booking becomes binding

3Key trade-offs

ChoiceCost we accepted
No loginAnyone can act as anyone
One writer at a timeOthers wait (up to 5 s)
Live validationThe page re-runs on every change
Shared reviewer inboxRead state shared by all reviewers
Single-day eventsNo overnight or recurring events

4Testing & validation

182automated tests, all passing
38business-rule tests (exact messages)
26UI tests on the real Streamlit app
12end-to-end demo scenarios automated
  • Mutation check: we deliberately changed the overlap query's < to <=, and 3 tests failed. Concurrency check: with a second writer holding the lock, nothing was written twice. Rollback tests: injected failures undo the whole change
  • AI was directed, then checked: each member caught a real AI mistake, e.g. an overlap check using <=, or a form that only validated after submit

5Known limitations

  • No real identity; single-day events only
  • In-app notifications only; blocks have no history
  • Local time; SQLite suits a single campus

6What we'd improve next

  • SSO with per-person permissions and inboxes
  • Email and .ics calendar export
  • Recurring events, analytics, venue suggestions
